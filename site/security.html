Security Model

Stylesmith modifies VS Code's installed workbench and may update product.json. This page explains those changes, the controls around them, and what they cannot guarantee.

Core Pillars

  • Content Security Policy
  • Workbench checksum
  • File changes and recovery
  • Workspace settings

Content Security Policy (CSP)

The Risk

A content security policy restricts some browser resource loads. It does not isolate trusted extensions or custom scripts from the privileges of VS Code's workbench.

The Fix

Stylesmith keeps the workbench's existing CSP and adds SHA-256 hashes for the inline scripts it inserts. With remote imports on, it adds https: to style and font sources; it also adds data: for fonts. Existing policy sources are retained.

Why It Matters

A script hash identifies the exact bytes allowed by that CSP entry; it does not sandbox the script or show that it is trustworthy. Custom JavaScript runs in the workbench context with the privileges available there. Only add code you trust.

Workbench checksum

The Risk

VS Code can compare the workbench with the checksum recorded in product.json and show an integrity warning when they differ. The warning may be hidden by settings or other changes, and a mismatch does not identify who changed the file.

The Fix

When warning suppression is enabled and VS Code tracks this file, Stylesmith writes a checksum for the workbench content it generated to product.json. This can suppress the warning for that content; it is not an authenticity check.

Why It Matters

Suppressing the warning can make other changes harder to notice. Turn suppression off if you want VS Code to report that its recorded checksum does not match the workbench.

File changes and recovery

The Risk

VS Code updates can replace or change installed workbench files. A patch may stop applying or behave differently after an update; Stylesmith cannot guarantee that every version will start normally.

The Fix

Before writing, Stylesmith checks that its marked patch can be removed from the source string. It writes through a temporary file and rename to reduce the chance of leaving a partial file. These steps do not cover every crash or external file change.

Why It Matters

Disable attempts to remove Stylesmith's marked content and bundled fonts and restore managed settings. The uninstall hook attempts only workbench and font cleanup; run Disable first to restore settings. If cleanup fails or VS Code will not start, repair or reinstall VS Code.

Workspace settings

The Risk

A project can contain workspace settings and files, but its settings must not select Stylesmith imports or cause project files to be loaded by Stylesmith in an untrusted workspace.

The Fix

Stylesmith reads imports from user settings, not project settings. In untrusted workspaces it refuses ${workspaceFolder} and ${cwd} path substitutions. This does not control other extensions, tasks, or code you run in VS Code.

Why It Matters

Untrusted workspace protections cover Stylesmith's import sources only; keep using VS Code's workspace trust controls and review other extensions separately.

VS Code's workbench integrity warning

Stylesmith changes workbench.html, so VS Code may report an integrity warning when the recorded checksum does not match. If warning suppression is enabled, Stylesmith may update that checksum for its patched content. If you see an unexpected warning, check the Stylesmith setting, recent VS Code updates, and whether another tool changed the installation.

A warning or checksum mismatch is not proof of malware, and no warning is not proof that the installation is unchanged. The checksum reports whether file content matches the value in product.json; it does not establish who produced that content. Disable Stylesmith if you want to return to the workbench content it can restore. If VS Code still behaves unexpectedly, repair or reinstall VS Code.
